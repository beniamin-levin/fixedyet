# FixedYet design

First written 15 September 2026. Revised 21 October 2026 after an independent review. Status: on hold, nothing is built yet.

The pitch: an agent that does not answer a bug report until it has run the reported code at the reported version, run it again against the fix, and can show you both results.

## What changed on 21 October

- **Evaluation uses SWE-bench.** A subset of SWE-bench Lite or Verified replaces the 50 hand-picked closed issues. Each instance comes with a base commit and the patch that fixed it, so the labels are free.
- **The sandbox decides the verdict.** The model proposes a reproduction test. A bug counts as reproduced only if that test fails at the reported version and passes with the fix. Confidence comes from rules over the run results, not from the model.
- **The reproduction is a pytest test.** It asserts the expected behaviour, so it fails while the bug is present. This replaces the exit-code script and matches how SWE-bench and SWT-bench define a reproduction.
- **Environment setup is tested on day one.** Rebuilding an old version of a repository is the biggest risk, so the first day tries SWE-bench's prebuilt images as the sandbox base.
- **A thin MCP server is in scope.** It exposes two tools, `reproduce_issue` and `check_fixed`.
- **The agent loop is hand-written** on the OpenAI client, with no LangChain or other agent framework, so every line can be explained in an interview.
- **Cut:** the parallel bisect, the GitHub App, Node and Go support, applying labels, and any interface beyond a demo page.
- **The tool never posts on other people's repositories.** Reports go to a file, or to a comment on a demo fork the author owns.
- **The plan is now nine days,** 22 to 30 October. It replaces the four-hour city-prize plan and the six-week GitHub App plan.

## How it works

Live mode takes a GitHub issue URL. Eval mode takes a SWE-bench instance ID. Both produce a markdown report and the sandbox image IDs needed to rerun every step.

1. **Intake.** Fetch the issue, its comments and the reporter's stated version through the GitHub API. Nemotron 3 Super extracts a repro contract: the version, the setup, the code to run, the expected behaviour and the observed behaviour. If the issue has no runnable snippet, the run stops with the verdict "needs info".
2. **Build the baseline checkpoint.** Start from SWE-bench's prebuilt image when one exists. Otherwise start from a slim Python image, clone the repository, check out the reported version and install it in editable mode. Run the existing test suite once as a sanity check, then save the result as a non-disposable image. That image is the baseline checkpoint, cached per repository and version.
3. **Write the reproduction test.** The agent loop has four tools: read a file, search the code, write a test, and run pytest. Every attempt runs in a disposable fork of the baseline, so failed attempts leave nothing behind.
4. **Run both sides concurrently.** One fork runs the test at the reported version. A second fork applies the fix side, which is main in live mode or the known patch in eval mode, then reinstalls and runs the same test. Each side runs twice to catch flaky tests.
5. **Decide by rules.** The matrix below turns the results into a verdict and a confidence level. The model cannot override it.
6. **Gather web evidence.** Tavily searches the error text for duplicates and upstream reports, and Tavily Extract reads changelogs to name the release that contains the fix. The fixing commit is found on a best-effort basis from commits and pull requests that mention the issue number.
7. **Write the report.** Nemotron writes the root-cause paragraph and the next actions from the evidence. The report is written to a file.

The decision matrix:

| Reported version | Fix side | Verdict |
|---|---|---|
| test fails | test passes | fixed on main, which counts as reproduced in eval mode |
| test fails | test fails | open bug, with evidence attached |
| test passes | test passes | not reproduced, and the web evidence decides between environment, configuration and needs info |
| test passes | test fails | inconsistent, meaning a bad test or a regression on main, never reported as reproduced |
| setup or collection error | any | needs info or unsupported project, with no guess |

Confidence is high when both runs agree on both sides. It is low when the two runs on either side disagree.

Where each sponsor technology is essential:

| Technology | Role | Why it is load-bearing |
|---|---|---|
| Nemotron 3 Super on Token Factory | intake, the test-writing loop, the report | the 256K context Token Factory serves takes the whole thread plus the source files read from the image |
| Nemotron 3 Nano on Token Factory | scoring search hits, summarising logs | a cheap second model shows deliberate model selection |
| Token Factory Sandboxes | baseline checkpoint, concurrent forks for both sides, disposable forks for test attempts | branching from a saved image is the product's core primitive |
| Tavily search and extract | duplicates, upstream reports, changelogs | new information the model has never seen |

The assessment schema, defined as a Pydantic model:

```json
{
  "verdict": "fixed_on_main | open_bug | not_reproduced | inconsistent | needs_info | unsupported",
  "confidence": "high | low",
  "confidence_basis": ["both runs agree on both sides"],
  "reproduction": {
    "repro_test": "tests/test_issue_1234.py",
    "reported_version": {"ref": "v2.31.0", "outcome": "fail", "runs": 2, "checkpoint_image": "uuid", "log_excerpt": "..."},
    "fix_side": {"ref": "main | gold_patch", "outcome": "pass", "runs": 2, "checkpoint_image": "uuid", "log_excerpt": "..."},
    "fixing_commit": "sha or null",
    "fixed_in_release": "version or null"
  },
  "not_reproduced_reason": "environment | configuration | not_an_issue | needs_info | null",
  "root_cause": "one paragraph with file and line references",
  "evidence": [{"kind": "duplicate | upstream | changelog | log", "url": "...", "why": "..."}],
  "next_actions": ["..."]
}
```

## Evaluation

The evaluation is what turns "we reproduce before we answer" from a slogan into a measured claim.

- **Dataset.** 15 to 30 instances from SWE-bench Lite or Verified for the deadline, up to 50 if time allows. Prefer light pure-Python repositories such as requests, flask, pylint and sympy. Each instance supplies the base commit and the patch that fixed the bug.
- **Mapping.** The base commit plays the reported version. The base commit plus the patch plays main.
- **Success.** The agent's own test fails at the base commit and passes with the patch. The agent never sees the patch or SWE-bench's own tests.

Metrics published in the README:

| Metric | Definition |
|---|---|
| Reproduction rate | the test fails at the base commit and passes with the patch |
| Wrong open-bug rate | the test fails on both sides, so the verdict wrongly says the bug is still open |
| Not reproduced rate | the test passes at the base commit |
| Setup failure rate | the environment could not be built |
| Cost per issue | Token Factory tokens at list price, plus Tavily credits |
| Wall time per issue | from issue to report |

The README also lists every failure with its cause. A live check on three to five open issues backs up the numbers, with the reports kept local.

Nemotron may have seen SWE-bench issues and their fixes during training. The README says so, and the live runs on open issues are the check against it.

## Stack

- Python 3.14, the version in the existing `.venv`. The Sandboxes SDK supports Python 3.10 to 3.14.
- The OpenAI Python client pointed at the Token Factory base URL. Nemotron 3 Super is `nvidia/nemotron-3-super-120b-a12b` at $0.30 input and $0.90 output per million tokens, with a 256K context. Nemotron 3 Nano is `nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B` at $0.06 and $0.24, and is the model to develop against.
- `contree-sdk` for Sandboxes, version 0.3.6 when this was written. It has an async client, `Contree`, and a sync client, `ContreeSync`. Its subprocess-like interface is not yet available on the async client.
- The Tavily Python client, httpx for the GitHub API, Pydantic, the MCP Python SDK, pytest and GitHub Actions.

## Risks

- **Environment rebuild** is the biggest risk, and SWE-bench spent most of its own effort on it. Prebuilt images come first, light pure-Python repositories are the fallback, and setup failures are reported as their own metric.
- **False reproductions.** Models write tests that "reproduce" bugs that are not there, and Metabase reports this about its own bot. The two-sided rule, two runs per side and the inconsistent verdict guard against it.
- **Training contamination** on SWE-bench is disclosed in the README and checked against the live runs on open issues.
- **Repositories that need services** such as databases are unsupported, and the tool says so.
- **Issue text is untrusted.** The model treats it as data, snippets only ever run inside the sandbox, and Tavily's injection filtering covers the web side.
- **Sandbox beta limits** cap concurrent operations at 50. A single run uses only a handful.
- **Clean room.** This is a new repository with fresh prompts and a generic schema, working only on public GitHub issues. Nothing from Netcracker goes near it, including the ticket-assessment skill and the Jira flow.

## Positioning

Market check on 21 October 2026. The closest prior art is Metabase's open-source Repro-Bot, MIT licensed. It already checks a bug at the reported version and on master and reports "seen fixed". It differs in four ways: it works only on Metabase, the model decides the verdict, its prompt forbids web search, and it runs inside Claude Code. Cite it in the README.

Other tools that run code against an issue all work on the default branch only: the OpenAI cookbook issue investigator, Vercel's sandboxed triage template, the Daytona and Flue bug-fix guide, Cloudflare's internal reproduce skill, Astro's triagebot and Ghost Hunter. Osloq, a paid reproduction service, was not reachable on 21 October. Dosu and GitHub's agentic triage workflows label and answer issues without running code.

The large coding agents go straight to a fix: GitHub Copilot's cloud agent, OpenHands, mini-swe-agent, Devin, Jules, Codex cloud, the Claude Code GitHub Action, Cursor and Factory. Reproduction is at most a step inside their prompts, never an output.

What no tool combines:

- pinning the reported Python package version, then a second run on main or the fix;
- a rule-based verdict that the sandbox decides, not the model;
- web evidence for duplicates and upstream reports;
- a published success rate and cost per issue. No product publishes its cost per issue, and Nemotron has no published result on a reproduction benchmark.

The pitch: triage bots answer from documentation and code search, and coding agents try to fix the issue outright. This one proves whether the bug exists at the reported version and whether it is already fixed, and it hands the maintainer the checkpoint to see for themselves.
